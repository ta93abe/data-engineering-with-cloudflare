## Plan Review: GitHub / Linear / Withings to R2 Parquet Migration

### What is done well

- The plan is exceptionally well-structured with clear chunk/task/step decomposition, following a consistent TDD pattern (write failing test, run, implement, run, commit).
- The R2 key layout is clearly documented and aligns with Plan B semantics (master=single, time-series=daily, snapshot=single).
- The parquet encoder code follows the established pattern in `parquet.ts` exactly (using `ensureWasmInit`, `arrowToParquet`, `extractColumn`).
- Row type definitions include appropriate nullable fields with `| null`.
- The commit granularity is sensible -- one commit per encoder group, one per service migration.

### Issues Found

#### Critical (must fix)

**1. Linear test mocking will not work with multiple sequential GraphQL calls**

The Linear test at line 1214-1287 calls `mockLinearGraphQL` three times, each adding an interceptor for `POST /graphql`. However, all three intercept the same `path: "/graphql"` and `method: "POST"`. The `undici` `fetchMock` intercepts are consumed in FIFO order, so the test implicitly relies on `runSync` calling issues first, then projects, then labels -- in exactly that order. This is fragile and undocumented.

The plan should explicitly document this ordering dependency, or better yet, the `mockLinearGraphQL` helper should inspect the request body to determine which query is being made. As written, if the implementation calls labels before projects, the test will silently pass with wrong data.

**Recommendation:** Add a comment in the test noting the mock consumption order, or switch to a body-inspecting mock approach.

**2. GitHub `syncRepos` writes repos with `owner_id: 0`, then `runSync` rewrites the file**

At plan lines 982 and 1052-1070, the `syncRepos` function writes `owner_id: 0` for all repos, then `runSync` immediately re-encodes and re-writes the file with the correct `user.id`. This is wasteful -- it writes to R2 twice for the same file in a single sync. Since `syncUser` is called first and returns the `User` object, the user ID is already available.

**Recommendation:** Pass `user.id` to `syncRepos` so it writes the correct `owner_id` on the first write. This eliminates the double-write and simplifies `runSync`.

**3. GitHub commits overwrite per-repo rather than merging across repos**

At line 1036-1038, the plan notes "For simplicity, overwrite per repo sync -- commits are append-only and idempotent by sha in downstream." However, if two repos have commits on the same day, the second repo's commits will overwrite the first repo's file at `github/commits/{day}.parquet`. This is a data loss scenario.

The plan acknowledges this with "in downstream" deduplication, but since only the last repo's commits survive per day, there is nothing to deduplicate -- the earlier repos' data is simply gone.

**Recommendation:** Either (a) include repo name in the R2 key (`github/commits/{repo_name}/{day}.parquet`), or (b) read-merge-write (read existing file, append new rows, deduplicate by sha, write back), or (c) explicitly document this limitation and confirm it is acceptable for the use case (single-user with few repos where same-day commits across repos are rare).

#### Important (should fix)

**4. Linear service rewrite (Task 5, Step 3) lacks full implementation code**

Task 4 (GitHub) provides the complete rewritten service code (lines 889-1117). Task 5 (Linear) at line 1297 says only "Full rewrite of sync functions -- replace all `db.prepare(...)` with Parquet encode + R2 put. Keep GraphQL client and types unchanged. Follow exact same pattern as github.ts rewrite."

This leaves significant implementation details for the agent to figure out, including how to map Linear's GraphQL response fields (`createdAt`, `updatedAt`, `startedAt`, etc.) to the row types (`created_at`, `updated_at`, `started_at`), how to serialize `labels.nodes` to the `label_names` JSON string, and how `description_length` is computed. An agent implementing this step would need to read the existing `linear.ts` carefully to understand these mappings.

**Recommendation:** Provide the full implementation code for `linear.ts`, or at minimum provide the key mapping logic (camelCase to snake_case field mapping, `labels.nodes.map(l => l.name)` to JSON string, `description?.length ?? 0`, etc.).

**5. Withings service rewrite (Task 6, Step 3) also lacks full implementation code**

Similar to Task 5, the Withings rewrite at lines 1529-1536 provides only bullet-point guidance. The Withings API has particularly complex response structures (measure groups with nested `measures` array containing `type`/`value`/`unit` that need to be decoded, e.g., `value * 10^unit`). The plan's test mock at line 1428 shows raw measure data (`type: 1, value: 70500, unit: -3` = weight 70.5kg), but the implementation code showing how to decode these measure types into the flat `WithingsMeasureRow` fields is not provided.

**Recommendation:** At minimum, provide the measure-type-to-field mapping logic and the `value * Math.pow(10, unit)` conversion code.

**6. `GitHubRepoRow.is_private` uses `boolean` type -- potential Arrow/Parquet compatibility issue**

At plan line 169, `is_private` is typed as `boolean`. The existing Oura encoders only use `string`, `number`, and `number | null` types. Apache Arrow's `tableFromArrays` infers the Arrow type from the JavaScript values. While Arrow does support boolean, `parquet-wasm` behavior with boolean columns should be verified. If it does not work, the plan will silently fail.

**Recommendation:** Add a specific test case that verifies a boolean column round-trips correctly through `arrowToParquet`, or convert to `number` (0/1) to match the safer pattern used by Oura.

**7. GitHub test does not set up `sync_state` updates or verify them**

The Oura tests verify that `sync_state.last_sync_at` is updated after a sync. The GitHub test (lines 779-855) does not test this. Looking at the planned `runSync` for GitHub (lines 1044-1088), there is no `sync_state` update at all. The GitHub service does not seem to track incremental sync state, which is fine for master/snapshot data, but commits could benefit from incremental fetching. This is a design gap rather than a bug, but should be documented.

**Recommendation:** Add a comment in the plan noting that GitHub sync is always a full refresh (no incremental sync_state tracking), and whether this is intentional.
